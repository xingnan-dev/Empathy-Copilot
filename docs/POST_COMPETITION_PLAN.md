## 3. 恢复设计要求

### 3.1 调用与执行尝试

- 逻辑调用表示某案件中的一次调查查询需求。一次逻辑调用可以有多次尝试。
- 每次尝试有独立身份、序号、状态、时间、失败信息和结果 Evidence 引用。
- 原失败尝试保留。新的人工恢复请求创建后续尝试，并记录关联、请求 ID、操作人声明、原因和时间。
- 同一恢复请求 ID 绑定固定目标和固定请求内容。相同请求重复提交返回已记录结果或当前进度，内容不一致时拒绝。
- 同一目标最多允许一个有效的新尝试。检查、记录恢复决定和取得执行资格必须在同一次带修订号校验的快照写入中完成。
- 决策和执行器使用同一套有效尝试选择规则。被后续恢复接替的历史失败记录继续可查，但不会永久阻塞已成功恢复的逻辑调用。
- 原先参数哈希仅用于兼容已有逻辑调用。后续尝试独立编号，避免再次被原调用的去重逻辑拦截。

优先沿用现有 State JSONB 和 ToolCallRecord。新增关联字段采用兼容旧快照的默认值。D2 必须确定旧记录的规范化规则、字段校验与 schema_version 处理，禁止给旧记录补造无法证实的执行时间或历史事件。

### 3.1.1 D2 必须冻结的执行规格

下列为 W1 设计与 W2 实现的共同验收要求，函数与字段调整均需在 D2 中列出最终定义。

| 位置 | 必须确定的行为 |
| --- | --- |
| `BusinessToolExecutionService._execute` | 普通调用遇到已有 COMPLETED 时复用结果；遇到已有 PENDING、RUNNING 或 FAILED 时继续阻断。只有恢复入口已经原子领取的新尝试，才允许进入恢复执行路径 |
| 同类中的 `_replace_call` 及记录构造处 | 同一次尝试的 PENDING → RUNNING → 完成可更新该尝试记录；新的尝试追加独立 ToolCallRecord，禁止覆盖前一次尝试 |
| `DeterministicDecisionPolicy.decide` 中的 `unsafe_tool_call` | 按显式接替关系找到各逻辑调用的当前有效尝试，再判断阻塞；禁止凭列表末项跳过没有被合法接替的失败 |
| 决策策略中的完成检查 | 与执行器共用同一逻辑调用及有效尝试识别规则，避免一方认为已完成、另一方认为仍阻塞 |
| 恢复入口 | 先检查已记录的恢复请求 ID 与请求内容，再处理新请求的修订号校验；已接受请求的重放不能创建新尝试 |
| 新尝试的执行资格 | 明确限定为本次成功领取的执行者。重复 HTTP 请求只读取进度；服务重启后仍遵循人工恢复规则，不能仅凭记录中存在 PENDING 就执行 |

仅把原来的任意状态早退改成“只有 COMPLETED 才早退”会放开未授权的失败重跑，不能作为实现方案。数据库修订号比较保证竞争领取的原子性，成功领取后的执行流程和请求重放仍需独立约束。

D2 的字段表至少明确逻辑调用身份、独立尝试 ID、前序尝试引用、尝试序号、恢复请求及内容绑定、操作人声明、恢复原因和时间。既有 `attempt_count` 从 PENDING 的 0 变为 RUNNING 的 1，W1 必须明确是否继续保留这一含义；新增序号字段不能直接复用该字段而改变旧数据解释。

### 3.1.2 旧快照兼容验收

`extra="forbid"` 拒绝输入中的未知字段。新代码加载缺少新增字段的旧快照，主要取决于字段默认值及新增校验规则。两种风险需分别测试。

- 优先采用新增字段带默认值的增量模型，旧记录缺少恢复信息时按历史单次调用解释。新增校验只对存在的恢复结构执行，继续保留原生命周期与 Evidence 引用校验。
- 使用比赛提交版本和 E3.1 格式的真实序列化样本，覆盖 COMPLETED、FAILED、PENDING、RUNNING 记录，验证读取和正常保存。原来缺少的字段继续保持缺省或未知。
- 坏数据仍须拒绝，包括无效前序引用、重复尝试身份、跨调用接替、循环关联和请求 ID 内容冲突。
- W1 明确 schema_version 是否变化。若变化，必须指定加载映射位置，并验证关系表元数据与映射后 State 的一致性；禁止在加载时只改 State 版本使元数据检查失配。
- 本轮要求新代码读取支持的旧快照。旧程序读取带新字段的快照可能被 `extra="forbid"` 拒绝，回滚说明必须写明这一方向的限制。

### 3.2 恢复资格

| 当前情况 | 本轮处理规则 |
| --- | --- |
| 已暂停，允许清单内只读调用为 RETRYABLE 失败 | 操作者明确触发后允许创建新尝试 |
| 重启后读到 PENDING / RUNNING | 先确认原工作进程已退出，再显式标记中断并创建后续尝试 |
| 原工作进程可能仍在执行 | 拒绝强制接管，保留暂停状态并返回原因 |
| NON_RETRYABLE 或 UNKNOWN_OUTCOME | 保留人工处理边界，恢复接口拒绝执行 |
| 业务终态、错误案件、错误目标或步骤预算不足 | 拒绝执行 |
| 存在其他未解决的人工审核或安全原因 | 保留该暂停原因，禁止借工具恢复绕过 |
| 旧修订号或目标已被其他请求接管 | 返回冲突，工具执行次数不增加 |

本轮执行环境采用本地单工作进程生命周期管理。实验脚本负责启动、终止并等待原子进程退出，才允许中断恢复。仅凭超时或 RUNNING 记录的年龄无法证明旧执行者已退出。通用跨主机接管需要额外的执行者隔离机制，应独立设计。

旧工作进程退出这一前置条件由实验脚本保证，应用入口只记录操作者对退出条件的声明。该记录无法充当运行时存活检测或 fencing 机制。演示应明确展示脚本等待子进程退出的证据，并说明实际部署必须具备对应的执行者生命周期约束。

恢复操作中的安全性分为两层验收。竞争恢复请求必须在执行前分出胜负；执行后的业务信息可能变化，返回结果应记录真实来源和新的观察时间。

### 3.3 应用入口和权限边界

拟提供 `POST /cases/{case_id}/tool-recoveries`，路由最终按现有 API 命名风格实现。

请求至少携带目标调用 ID、恢复请求 ID、expected_revision、操作者标识和恢复原因。成功响应携带逻辑调用及尝试身份、最新案件状态与修订号。运行中重复请求返回已记录的进度。修订号冲突返回 409，非法状态与禁止恢复的目标返回明确的业务错误。

演示入口限定本地受控环境。操作者输入只作为操作记录，不能宣称为经过身份认证的审计证据。若后续接入已有身份系统，操作者身份应由服务端认证上下文提供。

恢复服务复用 StateTransitionService，分别记录行动意图和生命周期状态。每次正式转换按原规则推进修订号及步骤计数。恢复前检查完成一次尝试所需预算，预算不足时保持可解释的暂停结果。

### 3.4 结果和证据

- 成功结果通过现有 Grounding 服务转成 Evidence，工具记录链接真实 Evidence ID。
- 空查询结果可以完成调用，不能制造占位证据。
- 失败或中断尝试没有成功证据，历史失败信息经过脱敏。
- 重复读取同一源记录沿用原有证据去重约定。若源记录发生变化，设计记录需明确新观察如何表达，避免相同 Evidence ID 对应不同内容。
- 工具恢复结束后重入正常工作流，重新计算信息缺口及下一步行动。

F0–F12 使用固定版本的静态业务样本，报告记录样本版本或摘要。相同源记录 ID 的内容不变是本轮证据去重实验的前提。可变源记录下的版本化证据语义需另行设计，本轮实验不能证明它已得到解决。

## 5. 故障注入与验收矩阵

先保存案件初始快照，再启动工作子进程。子进程通过明确握手通知已完成某次数据库提交，父进程据此终止它并等待退出，然后启动新进程加载案件。固定睡眠时长不作为到达故障点的依据。

调用计数保存到独立 PostgreSQL 观测表，按实验和尝试分组，记录工具入口及返回边界。测试表与案件快照分开提交。计数仅用于实验观测，真实业务写入是否完成必须由业务系统自己的提交记录证明。

| 编号 | 场景 | 必需断言 |
| --- | --- | --- |
| F0 | 无故障完成订单查询 | COMPLETED；来源正确；Evidence 引用有效；工作流继续 |
| F1 | 初始案件已保存，PENDING 写入前终止 | 无工具记录；重启后允许正常调用；正常完成调用总数为 1 |
| F2 | PENDING 已提交，RUNNING 写入前终止 | 启动后不会自动执行；确认旧进程退出并人工恢复后只执行新尝试 |
| F3 | RUNNING 已提交，工具入口前终止 | 启动后暂停；恢复前工具入口计数为 0；恢复后为 1 |
| F4 | 工具返回后，COMPLETED 提交前终止 | 快照仍无已完成结果；人工恢复可再次只读查询；两次尝试的事实如实保留 |
| F5 | COMPLETED 已提交后终止 | 重启无重复调用；证据与完成记录一并存在 |
| F6 | 只读工具超时 | RETRYABLE；无成功证据；人工恢复成功后原失败记录仍可查 |
| F7 | 同一恢复请求重复提交 | 关联同一后续尝试；不会新增执行 |
| F8 | 两个进程竞争恢复同一调用 | 恰好一个领取成功；失败方返回冲突；失败方执行计数为 0 |
| F9 | 恢复过程中再次终止进程 | 后续启动仍暂停；再次人工恢复后可继续；此前所有尝试可追溯 |
| F10 | 非法恢复目标或状态 | UNKNOWN_OUTCOME、NON_RETRYABLE、业务终态、预算不足和未解决安全原因均被拒绝 |
| F11 | 旧版本 State 与原正常调查路径 | 可校验、可加载、可继续；原已完成工具不重复执行 |
| F12 | 独立测试 fixture 已写入标记后丢失回执 | 产生 UNKNOWN_OUTCOME 并暂停；恢复接口拒绝重试；标记计数不增加 |

F4 中人工恢复后的额外只读查询是被明确允许的行为，报告应列出真实次数。F12 只验证未知结果分类和阻断，不覆盖外部业务对账。fixture 仅在测试注册表中接入。

先逐一通过各场景，再对进程和并发场景重复执行以排查偶发竞争。报告必须注明重复次数和覆盖范围，避免以重复次数替代故障点覆盖。

## 6. 执行命令与报告

环境采用仓库已有 Python 依赖、Docker Compose 和 PostgreSQL。安装和数据库配置按 README 执行。PostgreSQL 测试夹具会重建 public schema，必须使用独立测试库。

从仓库根目录运行以下既有检查。

```powershell
python -m pytest -m postgres
python -m pytest
python -m ruff check .
python -m mypy
```

首条命令前配置指向隔离测试库的 `TEST_DATABASE_URL`。缺失变量而被跳过的关键用例不得计入通过。实现时为故障实验补充一条可复制的脚本命令及必要环境说明。

故障报告至少包含代码提交号、环境版本、实验 ID、场景、注入边界、运行次数、预期与实际状态、尝试链、工具入口与返回计数、证据引用、通过/失败/跳过及原因。

## 7. 交付演示与贡献记录

三分钟演示按以下顺序进行。

1. 约 30 秒介绍案件与证据来源，展示一次正常查询。
2. 约 45 秒展示查询超时、失败分类和持久化历史，重启进程后读回同一案件。
3. 约 60 秒人工触发恢复，查询成功，案件进入下一条正常追问，展示失败与成功两次尝试。
4. 约 45 秒展示并发恢复冲突和故障矩阵报告，解释仍需人工介入的边界。

设计记录控制在 2–3 篇，覆盖尝试与恢复、并发和崩溃边界、快照及证据兼容。事后整理的记录标明补记时间。贡献说明关联真实提交、测试及本人做出的判断，AI 辅助部分按实际记录。

LLM 子串检查的语义局限在一处已知限制中记录具体反例。本轮验收聚焦恢复流程，报告不据此推导语言抽取质量或全面生产可靠性。

## 8. 最终完成标准

- 一个订单查询失败的案件，经进程重启和人工恢复后，可以继续正常调查。
- 原失败尝试、恢复决定和后续尝试均可追溯，Evidence 引用正确。
- 重复请求复用已有恢复，竞争请求在工具执行前受控。
- 恢复过程中再次崩溃，仍能保留状态并进入可解释的人工处理流程。
- F0–F12 实际通过，所需 PostgreSQL 与进程测试没有未解释的跳过。
- 原有测试、静态检查完成，旧快照兼容与安全边界有验证。
- 操作说明可供另一人在干净环境复现，演示报告只陈述测得的行为。
- 阶段评审完成后更新 PROJECT_STATE.md，标明实际完成内容及下一阶段入口。

达到这些条件后，项目可描述为“支持人工恢复的持久化客服调查 Agent，具备只读工具尝试追踪、并发恢复控制和可复现故障验证”。后续拓展以真实岗位目标和本轮验收结果为依据。
